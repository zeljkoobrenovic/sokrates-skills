# Sokrates configuration skills (`skills/config/`)

Skills that help an AI coding tool set up [Sokrates](https://sokrates.dev) correctly — the step *before* the analysis scanners in [`../scanners/`](../scanners/README.md) can do their work. Both are grounded in the Sokrates Java model (field references read from the source, including the places where the documentation is wrong), and both ship a checker that simulates Sokrates' own matching rules so a configuration can be verified without running Sokrates.

| skill | configures | checker |
|---|---|---|
| `sokrates-repo-config` | `_sokrates/config.json` for one repository: source scope (extensions, ignore rules, size limits), classification into main/test/generated/build/other, logical decompositions into components, concerns, goals and thresholds, git-history and contributor settings, tag rules, reusable `analysis_conventions.json` | `scripts/preview_config.py` — applies the config to the real tree: scope sizes, excluded files and why, components with LOC share, concern hits, dead or malformed rules, misclassified-looking files |
| `sokrates-decompositions` | `logicalDecompositions` in `_sokrates/config.json`: meaningful component structures — folder depth, mixed depth for monorepos, build-system modules, CODEOWNERS ownership, layers, technology, several decompositions side by side | `scripts/propose_decompositions.py` — measures every candidate on the real tree (files, LOC, share, balance score) and emits ready-to-paste config; verified with the repo-config preview |
| `sokrates-features-of-interest` | `concernGroups` in `_sokrates/config.json`: the features of interest Sokrates tracks across components — debt markers, deprecated/legacy code, feature flags, security-sensitive code, unsafe execution, error handling, integrations, telemetry, platform-specific code, domain vocabulary, integration libraries | `scripts/propose_concerns.py` — scans main files for ~28 catalog concerns plus the most-used external libraries, with hit counts, samples and paste-ready concern config |
| `sokrates-landscape-config` | `_sokrates_landscape/config.json` + `config-tags.json`, `config-teams.json`, `config-people.json`: discovery and layout, repository filters, virtual sub-landscapes, tags, contributor identity merging, bots, teams, embeds | `scripts/check_landscape.py` — discovers repository analyses like Sokrates does, previews thresholds, tags, virtual landscapes, and the contributor→people→teams pipeline |
| `sokrates-people-config` | `config-people.json` at repository (`_sokrates/`) or landscape (`_sokrates_landscape/`) level: contributor identity merging from git history with explicit, confidence-rated rules; hand edits preserved | `scripts/build_people_config.py` — builds the file and `config-people-for-review.json` (every merge with its rules and evidence, items to review first, candidates not applied); verified with the landscape checker |
| `sokrates-virtual-landscapes` | `virtualLandscapes` in `_sokrates_landscape/config.json`: meaningful sub-landscapes by repository-name patterns — from the user's grouping (products, teams, org units) or from the analyses (naming conventions, folders, technology, activity, contributor domains, shared committers, tags), nestable | `scripts/propose_virtual_landscapes.py` — measures every candidate grouping and a user-supplied one (members, LOC share, coverage, remainder, overlaps) and emits paste-ready config; verified with the landscape checker |

Typical order for a new portfolio: `sokrates-repo-config` per repository → `sokrates-decompositions` → `sokrates-features-of-interest` → `sokrates generateReports` → `sokrates-landscape-config` → `sokrates-people-config` → `sokrates-virtual-landscapes` → `sokrates updateLandscape` → the scanners (`full-scan`) per repository.

Install: `ln -s "$(pwd)/skills/config/sokrates-repo-config" ~/.claude/skills/sokrates-repo-config` (same for the landscape skill).
